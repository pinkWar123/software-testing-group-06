## 1. Scope and workflow

Three endpoint groups are exercised by **one shared workflow** across every
scenario, as required:

| Group | Endpoint | Role in the workflow |
|---|---|---|
| Auth-heavy | `POST /api/login` (admin) | Logged in once per virtual thread (Once Only Controller), not re-logged-in every loop — models one admin session with many actions. Stress additionally runs a dedicated sub-test that deliberately fails login twice to validate the real account-lockout logic. |
| Read-heavy | `GET /api/admin/orders` | Returns the full `orders` ⋈ `users` join, no pagination — this turns out to matter a lot (§4). |
| Transactional | `PUT /api/admin/orders/:id/status` | Advances an order through its state machine (`pending → confirmed`). |

**Why this workflow, not the obvious consumer one:** a groupmate had already
built the login→search→cart→checkout flow. This workflow was chosen instead,
grounded in reading `backend/server.js` directly rather than guessing —
details and the SUT facts that came out of that reading (real admin
credential, DB-reset-on-restart behavior, missing admin-role check, a
transition-table logic bug) are in `AGENTS.md`'s "Known SUT characteristics"
section and `ai-audit/AI_Audit_Report.md` Entry 03.

**AI-first process:** every test plan below went through the same cycle —
AI-drafted design (posted for sign-off before any file existed) → generated
`.jmx` → smoke-tested against the real running backend → human-review pass →
fix (or an honest "no defect found") → commit. The full prompt/response log
for every step is in `ai-audit/AI_Audit_Report.md` (17 entries).

## 2. Task 1 — Load, Stress, Spike

### 2.1 Load — `23127102_Load_20260816.jmx`

**Design:** 10 threads (models a small back-office team), 20s ramp-up, 300s
(5 min) steady-state duration — not a fixed loop count, so the report reflects
a real steady-state window. Gaussian think-time (2000ms ± 800ms) between the
read and the update; a smaller Uniform timer (300-900ms) at the loop boundary.
Data-driven via `data/admin_login.csv` and `data/order_ids.csv` (generated by
`jmeter/seed_orders.js`, since the `orders` table is empty on a fresh DB —
seeding is a direct-DB script, deliberately kept separate from the measured
HTTP workflow). Listener: **Aggregate Report**.

**What the AI got wrong, and why:** the first draft's Response Assertion on
the `PUT` sampler checked "response code is 200 or 400," which looks
sufficient but isn't — JMeter's `HTTPSampler` marks any response ≥400 as a
*failed* sample **before** assertions run, and an assertion can only turn a
pass into a fail, never the reverse. Since a `400 Invalid state transition` is
the *expected*, correct outcome once the seeded order pool is consumed, every
one of those would have shown as a false failure. The AI missed this because
"assertion passes ⇒ sample passes" is true for ordinary content assertions
and only breaks for this specific status-code-determination quirk, which
isn't obvious from JMeter's own UI. **Fix:** a JSR223 PostProcessor explicitly
setting `prev.setSuccessful(true)` on `400`, verified by smoke test
(`responseCode=400, success=true`). A secondary, more minor finding: no
think-time existed at the loop boundary in the first draft; added a small
Uniform timer.

**Real results (1,115 samples, live run):**
| Sampler | n | avg (ms) | p95 (ms) | Codes |
|---|---|---|---|---|
| Overall | 1,115 | 12.1 | 35 | 200×624, 400×491 |
| `POST /api/login` | 10 | 40.0 | 335 | 200×10 |
| `GET /api/admin/orders` | 556 | 18.7 | 40 | 200×556 |
| `PUT /api/admin/orders/:id/status` | 549 | 5.1 | 12 | 200×58, 400×491 |

0% error rate (by design — see §3). Healthy across the board at this
concurrency; sub-40ms p95 everywhere.

### 2.2 Stress — `23127102_Stress_20260816.jmx`

**Design:** two Thread Groups, run **sequentially**
(`serialize_threadgroups=true`) in one file. Main group: 80 threads (8x Load),
15s ramp-up, 180s sustained duration, reduced think-time (500ms±200ms). A
second, small lockout-validation group runs *after* the main group finishes:
2 deliberately wrong-password logins (`data/admin_login_lockout.csv`), then a
3rd attempt with the correct password, asserting the account is now locked.
Sequencing matters here — since all 80 main-group threads share one admin
account, running the lockout test concurrently would have cascade-failed
unrelated logins mid-measurement. Listener: **Summary Report**.
`jmeter/reset_lockout.js` added to undo the deliberate 180s lockout between
takes.

**What the AI got wrong, and why (the most important finding of this
homework):** the lockout group's three samples (two 401s, one 403) all showed
`success=false` in the smoke test, despite 401/401/403 being exactly the
*correct, expected* outcomes. The root cause was the **identical** JMeter
quirk just fixed in Load, minutes earlier — reproduced in newly-written
samplers. Fixing one instance did not generalize to new code written
afterward in the same session; each new element needed the same scrutiny
applied again. Fixed the same way (JSR223, `success = code == expected`).
Full reasoning in `ai-audit/AI_Audit_Report.md` Entry 08 and
`ai-audit/AI_Critique.md`.

**Real results (6,465 samples, live run):**
| Sampler | n | avg (ms) | p95 (ms) | Codes |
|---|---|---|---|---|
| Overall | 6,465 | 1,432.6 | 2,478 | 200×3664, 400×2798, 401×2, 403×1 |
| `GET /api/admin/orders` | 3,203 | 1,432.8 | 2,427 | 200×3203 (avg 1,716,940 bytes/response) |
| `PUT /api/admin/orders/:id/status` | 3,179 | 1,454.0 | 2,547 | 200×381, 400×2798 |
| Lockout: 2× wrong password | 2 | 3.0 | — | 401×2 |
| Lockout: verify locked | 1 | 4.0 | — | 403×1 |

0% error rate throughout — the backend survives sustained 80-thread load
without crashing, but average latency is ~118x Load's. §4 explains why
this isn't purely "80 threads is too many."

### 2.3 Spike — `23127102_Spike_20260816.jmx`

**Design:** three sequential Thread Groups forming a real low→high→low shape:
Baseline (5 threads/10s ramp/30s), Burst (150 threads/**3s** ramp/30s),
Recovery (5 threads/10s ramp/30s) — same workflow throughout. Listener:
**View Results Tree**. Official runs were executed headless (`-n`), per
Apache JMeter's own guidance against running View Results Tree live in GUI
mode under real load (memory risk at 150 threads) — documented in
`ai-audit/AI_Audit_Report.md` Entry 09.

**Human review:** unlike Load and Stress, this pass found **no new defect** —
the JSR223 fix was applied correctly to both `PUT` samplers on the first
attempt. Rather than force a finding, this was reported honestly (Entry 10).
The one deliberate design choice worth noting: the Burst group omits the
loop-boundary timer that every other group has, modeling genuine burst
intensity rather than many synchronized humans.

**Real results (2,210 samples, live run), segmented by phase — the number
that matters most here:**
| Phase | n | avg (ms) | p95 (ms) |
|---|---|---|---|
| Baseline (before) | 58 | 21.2 | 51 |
| Burst (150 threads) | 2,091 | 1,890.0 | 2,594 |
| Recovery (after) | 61 | 20.5 | 56 |

**The system fully recovers.** Recovery (20.5ms) is statistically
indistinguishable from Baseline (21.2ms) — within seconds of the burst
ending, performance is back to normal. This is the strongest, most
reassuring finding in the whole dataset, and it's only visible because the
phases were segmented instead of read as one blended average (see §3, finding
#3).

## 3. Task 2 — AI analysis and misinterpretation hunt

Full detail in `analysis/ai_analysis_raw.md`, `analysis/misinterpretation_hunt.md`,
`analysis/optimization_judgment.md`, computed from the real `.jtl`s via
`analysis/compute_stats.js`. Five real misinterpretations were found in the
AI's first-pass read of its own analysis:

1. **"0% error rate" hid that 85-98% of `PUT` calls were business-rejection
   `400`s**, not clean transitions (Load 58/549 fresh `200`s; Stress
   381/3179; Spike-burst 17/937) — a true statement that nonetheless implied
   "nothing interesting here," when most requests weren't hitting the code
   path they appeared to be.
2. **"GET and PUT degrade almost identically → broad concurrency saturation"
   ignored a real confound**: `GET /api/admin/orders` has no pagination, so
   its response size grew ~5x between Load and Stress (342,796 → 1,716,940
   bytes, tracking how many orders were seeded) while `PUT`'s payload stayed
   a constant ~335 bytes — yet `PUT` slowed by a similar *factor* anyway,
   pointing at Node's single-threaded JSON serialization blocking everything
   else, not thread count alone, as a major contributor.
3. **Spike's blended "overall avg 1,789ms" hid the Recovery finding
   entirely** (§2.3) — a single number covering three very different phases,
   dominated by whichever phase has the most samples (Burst, 94.6% of them).
4. **An implied linear thread-count relationship the data contradicts**:
   80→150 threads (1.875x) only produced a 1.32x latency increase
   (1,432.6ms→1,890.0ms) — sublinear, consistent with an already-saturated
   single-threaded bottleneck, not a proportional per-thread cost.
5. **Load's 10.6% `PUT` success rate (58/549 ≈ 1-in-9.5, close to the
   10-thread count) is a CSV-sharing collision artifact**, not evidence the
   endpoint "often rejects" updates — all 10 threads start `order_ids.csv` at
   row 1 with similar think-time pacing, so several threads race the same
   `order_id` and only the first gets a genuine transition.

**Optimization judgment** (full reasoning in `analysis/optimization_judgment.md`):
of the AI's 4 proposed fixes, **SQLite WAL mode** is feasible and genuinely
unset in this codebase; **a database index** and **a connection pool** are
judged hallucinated for this stack (the query is already keyed on indexed
primary keys, and SQLite is an embedded, single-writer database that doesn't
benefit from client-server-style connection pooling); **response caching** is
feasible but adds invalidation complexity to solve what a simpler fix already
solves. That simpler fix — **pagination/`LIMIT` on `GET /api/admin/orders`**
— is the one most directly supported by the AI's own analyzed data (the
`bytes` column) and the one it never proposed, defaulting instead to generic
database-performance vocabulary. That gap is the single most useful finding
of the judgment pass.

## 4. Task 3 — Continuous performance-testing proposal

Full proposal, flow chart, and cost/false-alarm trade-off table in
`proposal/continuous_performance_testing.md`. Summary: a path-filtered gate
(only run if `backend/**`/`jmeter/**` changed) feeding a smoke-vs-full split
(short reduced-scale Load on every PR/push; full Load+Stress+Spike+Soak
nightly/on-demand), compared against a rolling — not static — p95 baseline,
with a "regression must reproduce on a same-day re-run before failing the
build" rule aimed directly at false alarms from noisy shared CI runners.
